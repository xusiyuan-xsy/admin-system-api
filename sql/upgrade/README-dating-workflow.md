| 页面 | 路径 | 前端源码 | 功能 |
| --- | --- | --- | --- |
| 红娘分配 | `/dating/assignments` | `src/views/dating/assignments/index.vue` | 客户搜索、服务状态、剩余次数、红娘分配/转交、归属变更历史 |
| 配对服务 | `/dating/matches` | `src/views/dating/matches/index.vue` | 推荐、双方意向、预约、改期、取消、爽约、完成见面、服务事实、独立扣次结果、异常任务重试、扣次流水 |

推荐目前为人工选择客户并填写理由，不包含自动匹配评分、择偶条件筛选和推荐算法。红娘候选为启用且未删除的后台账号，业务角色及操作权限需在角色管理中另行配置。

## 核心规则

1. 创建推荐和新增/调整预约时，双方都必须为启用客户、有有效负责红娘、服务中状态、已收款订单和剩余次数。
2. 双方服务条件取购买时的权益快照，固定按 `ALL` 判断。套餐或服务选项后续修改不会改变已绑定规则。
3. A 只购买“加好友”，B 购买“加好友 + 见面”：加好友后只扣 A 一次，见面后再扣 B 一次；不要求两人同时满足。
4. 同一对用户按用户编号排序形成唯一配对；重复推荐、重复登记事实、多次见面和后续续单，均不会让同一参与方在该配对重复扣次。
5. 每个参与方固定绑定最初的权益与规则快照。不会因为续单自动改扣新权益。
6. 最新一次推荐必须分别记录两人愿意继续。未确认或有一方拒绝时，不能新增服务事实或安排见面。
7. “完成见面”只能通过预约的“确认见面完成”生成。预约、改期、取消、爽约均不属于已完成服务，不扣次。
8. 加好友及其他自定义服务选项通过服务事实登记，填写实际发生时间、核实记录及可选凭证编号。只能登记双方快照中存在的选项。
9. 实际发生时间不得晚于当前时间，不得早于配对建立；见面完成不得早于预约建立。事实及流水不提供普通编辑/删除入口。
10. 某人余额扣到 0 后，该权益为 `EXHAUSTED` 并记录耗尽时间，客户为 `NOT_RENEWED`；禁止继续新增推荐或预约。
11. 已发生的服务允许补录，但绑定权益已耗尽时，只接受耗尽前实际发生的事实。已在该配对扣过次的客户续单后，可以继续同一配对的服务，但不再扣新权益。
12. 未扣次但旧权益已在其他配对耗尽的参与方，不自动绑定续单。相关异常需主管核查，本阶段未提供手动改绑或补扣审批。

## 事务与补偿

- 服务事实和双方各一条扣次任务同事务落库。事实提交后，再分别启动独立扣次事务。
- 任意一方扣次异常，不撤销已保存事实，也不撤销另一方已成功的扣次。
- 每笔扣次事务同时写余额、权益状态、参与方结果、任务结果及扣次流水；最后一次还更新客户“未续单”状态。
- 客户记录按编号升序锁定，扣次按客户、参与方、权益、任务顺序锁定；数据库条件更新及唯一键共同防止超扣和重复扣次。
- 默认每 30 秒扫描到期 READY 任务，每批最多 100 条；异常延迟约 30 秒重试，累计 5 次异常转 ERROR。
- `dating.recovery.enabled=false` 仅关闭后台恢复扫描，不关闭服务事实提交后的即时扣次。
- `dating.recovery.delay-ms` 可调整扫描间隔；异常任务的重试延迟目前固定为 30 秒。
- 任务 DONE 表示已处理，不一定已扣次：结果可为 PENDING（条件未全满足）、BLOCKED（业务条件阻塞）、DEDUCTED（已扣次）。
- 条件未全满足无需人工重试，后续新增事实会建立新任务。ERROR 或 BLOCKED 可通过“扣次与流水”中的重试按钮重新核查。
- 详细技术异常写入后端日志，页面只显示通用异常提示，避免暴露数据库信息。

## 数据与权限

新增九张表：`dating_assignment_history`、`dating_pair`、`dating_pair_participant`、`dating_recommendation`、`dating_pair_intention`、`dating_appointment`、`dating_appointment_history`、`dating_service_event`、`dating_deduction_task`。

扩展客户 `matchmaker_id`、权益 `exhausted_at`，扩展权益流水 `pair_id`、`event_id` 及唯一键。OPEN 流水改用生成列 `opening_order_id` 单独保证每订单只开通一次，允许同一订单用于多个不同配对。

| 权限 | 用途 |
| --- | --- |
| `dating:assignment:list` | 分配列表及历史 |
| `dating:assignment:edit` | 分配、转交、红娘账号搜索 |
| `dating:match:list` | 配对列表 |
| `dating:match:query` | 配对详情及事实、流水 |
| `dating:match:add` | 创建推荐及候选客户列表 |
| `dating:match:intention` | 登记双方意向 |
| `dating:event:add` | 登记加好友等服务事实 |
| `dating:appointment:add` | 新增预约 |
| `dating:appointment:edit` | 改期、取消、爽约、确认完成 |
| `dating:deduction:retry` | 异常或阻塞任务重试 |
| `dating:service:all` | 跨负责人访问和操作本阶段婚恋服务数据 |

普通账号创建推荐时只能选择自己负责的两名客户；跨负责人推荐需管理员或 `dating:service:all`。已由主管建立的跨负责人配对，任一当前负责人可在具备对应操作权限时共同跟进。配对详情不返回手机号或付款信息，客户候选手机号脱敏。

分配转交同步影响新收费模块的客户、订单、权益可见范围。未分配客户回退到客户创建人，订单 `create_by` 不修改。收费跨负责人权限仍为独立的 `dating:billing:all`，不能用 `dating:service:all` 替代收款授权。

重要边界：旧 `/system/payingUser` 档案接口的原有全量查询、导出等权限没有在本次全面重构。普通红娘不能同时授予这些旧全量权限，否则仍可能通过旧入口访问其他客户档案。上线前必须核查角色授权；需要开放旧档案编辑时，应先单独完成该模块的数据权限改造。

2. 暂停业务写入、旧版本后端及扣次恢复任务。依次执行尚未完成的 `20261013_dating_billing.sql`、`20261013_dating_workflow.sql`、`20261013_dating_success.sql`，最后执行 `20261013_dating_comments.sql` 补齐中文表注释和字段注释。注释脚本要求三阶段结构一致，可重复执行。DDL 自动提交，不能当作可整体回滚的事务。
3. 部署前后端并重启后端。当前代码已依赖 `matchmaker_id` 等新字段及第三阶段终态约束，不能只部署代码、不执行迁移；成功结案默认关闭也必须执行第三阶段迁移。
4. 不要在业务库重跑 `ry_20260321.sql`、`association.sql`、`matchmaking_profile.sql` 等建库基线，它们含删表语句。升级只使用对应的增量脚本。
5. 管理员重新登录，在角色管理中配置页面及按钮权限。工作台使用者需要列表、详情及相应操作权限。分配、跨负责人操作、异常重试权限按职责授予，不默认授予所有角色。
6. 历史客户不会被自动分配；历史交友、见面、付款不会被推断或回填。先完成客户收费开通和红娘分配，再创建新推荐。
7. 使用测试客户完成下述验收，核查余额、流水、任务和状态后再正式启用。

## 验收清单

- A 购买加好友 3 次；B 购买加好友+见面 1 次。确认收款后分别分配红娘。
- 创建 A/B 推荐，未确认双方愿意时，预约及事实被拒绝；分别确认后可继续。
- 先预约，余额不变；改期、取消、爽约均不扣次。
- 重新预约，登记加好友：A 剩 2 次，B 仍剩 1 次。
- 确认实际见面完成：A 仍剩 2 次，B 变为 0 次，B 显示“未续单”，无法新增预约。
- B 续单后，同一配对再次见面不再扣 A/B 次数；换一个配对按新的实际条件正常判断。
- 两个配对争用某人最后一次余额，不得负数或产生两笔扣次。
- 一方扣次失败时，另一方正常提交；异常恢复或手动重试后不得重复扣次。
- 客户转交后，原负责人失去该客户订单访问权限；新负责人可以访问，历史创建人信息不变。
