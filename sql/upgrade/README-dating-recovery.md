## 2. 配置与运行语义

| 配置 | 环境变量 | 默认 |
| --- | --- | --- |
| `dating.recovery.enabled` | `DATING_RECOVERY_ENABLED` | `true` |
| `dating.recovery.delay-ms` | `DATING_RECOVERY_DELAY_MS` | 30000 |
| `dating.recovery.stale-ms` | `DATING_RECOVERY_STALE_MS` | 120000 |
| `dating.recovery.overdue-ms` | `DATING_RECOVERY_OVERDUE_MS` | 300000 |

`delay-ms` 是本批结束后的固定等待时间，也用于首次启动延迟。失联阈值需大于正常扫描间隔及预期处理时间；时钟需保持同步。每批最多读取 100 个已到期 READY 任务，保持原扫描上限。

- 先独立提交 RUNNING 标记，再逐任务事务处理，最后写本批结束结果。不把整个批次放在同一个业务事务中。
- 每次应用启动生成不含主机信息的实例 ID。概览只用当前实例的最近记录判断调度状态，不能拿旧进程成功记录冒充当前心跳。
- `NOT_STARTED` 为启动后尚无记录；超过失联阈值仍无首条记录转 `STALE`。关闭恢复时为 `DISABLED`。
- 批次状态为 `RUNNING/SUCCEEDED/PARTIAL/FAILED`。长时间未完成或未再运行的当前实例显示 `STALE`；历史遗留 RUNNING 数量另列，不擅自改写为成功。
- `scanned` 是选中的任务数；`processed` 是处理正常返回数，可能包含条件未满足、业务阻塞或并发已处理，**不是本批消费次数**。
- 任务调用异常记入 `failed`，失败历史写入也异常则计入 `recordFailures`。扫描查询失败记录 `FAILED` 和安全错误分类。
- 运行记录写入失败不会阻断正常扣次恢复；系统日志记录失败。数据库完全不可用时不能保证把故障写回同一数据库，必须由外部监控覆盖。
- 扫描成功不等于所有业务异常消失。队列的 `errors/blocked/overdue` 必须单独查看，计数单位是任务，不是客户或配对。

每实例默认约 2880 条运行记录/天，实际随处理耗时变化。当前本地运行不自动删除历史；正式运营前应明确保留周期、归档及容量监控。长期保留审计与高频运行记录应分别制定政策。

## 3. 接口与权限

以下为后端接口，不是页面路径。列表沿用 `pageNum/pageSize` 分页。

| 方法及路径 | 权限与范围 |
| --- | --- |
| `GET /dating/recovery/overview` | `dating:recovery:query`，当前实例调度状态、全局任务计数和超时 RUNNING 数 |
| `GET /dating/recovery/runs` | `dating:recovery:query`，全局恢复批次分页；不含客户详情 |
| `GET /dating/deduction-exceptions?pairId=...&kind=ERROR` | `dating:match:query`，沿用配对参与双方当前负责人范围；全局服务权限可查全部；kind 可选 ERROR/BLOCKED/READY |
| `GET /dating/deduction-tasks/{id}/history` | `dating:match:query`，先校验该任务所属配对权限，再分页查历史 |
| `POST /dating/deduction-tasks/{id}/retry` | 复用原 `dating:deduction:retry`，必填 JSON 原因，再次检查当前归属及终态，原子保存重试历史 |
| `GET /dating/deduction-tasks/{id}/follow-up` | `dating:match:query`，当前跟进及可用动作，仍需当前配对访问权 |
| `GET /dating/deduction-tasks/{id}/follow-up/history` | `dating:match:query`，先授权再分页，恢复后保留 |
| `POST /dating/deduction-tasks/{id}/follow-up` | `dating:exception:handle`，当前版本、动作、必填说明及可选进度/人工截止时间 |

异常列表包含：ERROR、DONE/BLOCKED，以及曾失败或超过待处理阈值的 READY。DONE/PENDING 表示条件未全部满足，不属于技术异常；DEDUCTED/STOPPED 不进入异常队列。历史页在成功恢复后仍能查看原记录。

安全错误分类：`DATA_CONFLICT`、`DATABASE_TRANSIENT`、`DATABASE_ERROR`、`BUSINESS_INVARIANT`、`PROCESSING_ERROR`；人工重试记录 `MANUAL_RETRY`。不按异常正文猜测分类，不将驱动异常或 SQL 返回客户端。

普通红娘无全局监控权限。异常及历史沿用配对协作范围：是任一方当前负责人即可访问该配对，不等同于获得另一方完整档案权限。双方均转交后，旧负责人立即失去历史访问权。新查询接口均为只读，不提供强制扣次、改绑或直接修余额能力。

实际工作台路径为 `/dating/recovery/index`，不是 `/dating/exceptions`。从“配对服务”进入，隐藏路由需 `dating:match:query`；全局监控标签另需 `dating:recovery:query`，不因能查看配对而自动授予。配对详情和工作台共用历史抽屉与重试弹窗。

人工重试现在必须提交 `{"reason":"已核对并修复相关问题"}`，原因非空白、最长 500 字，前后端均校验，去除首尾空白后保存。空请求体/空白/超长值均拒绝。前端二次确认后提交；提交未确认时须核对任务及历史，不能假定请求未执行。异常认领和跟进已实现，详见第 8 节。

## 4. 失败与恢复规则

- 每位客户仍按自己购买快照的全部选项独立判断，同对每人终身最多扣一次；不把恢复扫描变成新的消费依据。
- 单方扣次失败先回滚其业务事务，再以独立事务写入失败计数和历史；两者原子提交。失败历史不能写入时，计数也不提前提交。
- 同一重试等待窗口内的并发失败只累计一次，未到期的任务不会提前处理；已成功 DONE 或已 ERROR 的任务不会被迟到的失败报告覆盖。
- 失败重试等待仍为原来的 30 秒；累计 5 次转 ERROR，自动扫描不无限重试 ERROR。人工重试沿用原可重试条件，不解锁结案、改绑续单或绕过余额检查。
- 人工重试与重试历史同事务，历史写入失败则保留原状态与尝试次数；成功后不删除旧失败历史。
- 业务阻塞仍走原业务判断，不伪装成数据库异常，不自动修复余额；未满足条件不扣次。
- 完全退出的进程无法写“崩溃失败历史”，因此以未结束批次和原持久任务作为恢复依据，不能伪造一次已经落库的失败。
