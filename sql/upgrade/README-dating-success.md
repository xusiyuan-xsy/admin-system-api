# 成功结案模块部署与验收

更新日期：2026-10-13。依赖收费开通和服务执行模块。

## 升级步骤

1. 备份业务数据库，在预发布确认 MySQL >= 8.0.16。检查已有结构与脚本一致；重复执行不能修复其他分支造成的同名异构表或约束。
2. 暂停业务写入、旧后端和扣次恢复任务，避免迁移中继续处理服务。
3. 按顺序执行尚未完成的增量脚本：
   - `20261013_dating_billing.sql`
   - `20261013_dating_workflow.sql`
   - `20261013_dating_success.sql`
   - `20261013_dating_comments.sql`（三阶段结构核对一致后执行，补齐中文表注释和字段注释，可重复执行）
4. 部署当前后端及前端并重启。即使成功结案开关关闭，当前扣次代码也依赖第三阶段的终态约束，不能跳过第三份迁移。
5. 重新登录并配置角色菜单、列表、详情、结案权限。迁移不自动授予角色权限。
6. 业务确认成功核实标准及凭证规范后，设置 `DATING_SUCCESS_ENABLED=true` 并重启后端。默认 `dating.success.enabled=false`，禁止直接结案；无需为了查看历史案例开启该开关。
7. 在预发布用测试客户完成本文验收，再安排业务上线。

DDL 自动提交，不是可整体回滚的事务。不要在业务库重跑含删表语句的建库基线。回退需停止写入并使用事先验证的恢复方案，不能仅删除案例表或回退前端。

## 数据与权限

新增 `dating_success_case`、`dating_success_case_member`，分别保存案例和成员快照。案例表按配对唯一，成员按客户唯一，首版不支持结案后恢复或再次成功结案。

迁移扩展配对和预约的 `TERMINATED`、参与方的 `STOPPED`、任务的 `CANCELLED` 及结果的 `STOPPED` 约束。客户与权益使用既有 `SUCCESS_CLOSED` 状态；保留剩余次数，不生成虚假消费。

| 权限 | 用途 |
| --- | --- |
| `dating:success:close` | 结案及结案策略查询 |
| `dating:success:list` | 案例分页、筛选候选及统计 |
| `dating:success:query` | 案例详情、核实说明及凭证编号 |
| `dating:service:all` | 跨当前负责人访问，与功能权限共同使用 |

结案入口位于 `/dating/matches`，还需工作台的列表及详情权限；案例页面为 `/dating/success-cases`。普通用户按当前负责人限制可见范围；结案红娘筛选按历史快照，不改变访问权限。列表不返回核实证据，详情权限单独控制。

旧 `/system/payingUser` 全量查询、导出等权限未在本次统一改造，不能同时随意授予普通红娘。上线需核查旧入口，否则新模块的负责人隔离不能阻止旧接口的数据访问。

## 业务规则

- 必须有配对绑定的已收款有效/耗尽权益，最新推荐双方愿意继续，客户启用且未结案。
- 已未续单可以结案；未全部满足服务选项也可以真实脱单，不为结案补造事实。
- 必填实际成功时间、核实说明、凭证编号及双方确认勾选；时间在配对建立至当前之间。
- 同事务先结算相关配对已有事实，再关闭双方服务及有效/耗尽权益。各自全部条件满足才扣，每对每人最多一次。
- 未满足条件或业务阻塞不强扣；技术异常整体回滚。并发锁涉及所有直接相关配对的客户，按编号升序获取；配对集合变化则要求刷新重试。
- 终止双方的其他未结束配对及未完成预约，停止未扣次参与方；保留已完成事项、事实及流水。第三方权益不关闭。
- 双方未付款订单取消并记录案例原因；已付款订单不退款。重复提交返回原案例，不改写证据。
- 案例按配对去重、人数按客户去重。跨红娘案例平台总量只计一次，不可直接累加各红娘筛选结果。

## 验收清单

- 开关关闭时前端禁止结案，直接调用接口也拒绝；普通用户无权结案他人配对。
- 一方尚有余额，另一方未续单，真实脱单后均成功结案；余额不清零、不产生额外消费。
- 存在满足条件但尚未完成的扣次任务，结案前结算一次；条件不足一方不扣。
- 结算发生数据库错误时案例、余额、客户及配对状态全部回滚，可排查后重试。
- 双方其他配对和预约终止，第三方自身服务继续，终止记录包含原因和案例编号。
- 双击提交、两名操作员并发、扣次与结案并发均不重复消费或统计。
- 同一客户在不同配对同时结案只允许一个成功，不允许一人计入两个成功案例。
- 成功后不能新增推荐、登记服务事实、预约或收款恢复服务；未付款续单已取消。
- 日期、姓名、红娘筛选与统计一致；客户转交改变可见范围，不改变结案归属快照。
- 无详情权限无法读取证据，手机及桌面表单、详情和列表可正常使用。

## 验证命令

后端根目录：

```powershell
mvn -pl ruoyi-admin -am test
```

默认执行 32 项 H2 集成测试，6 项 MySQL 测试跳过。专项测试只接受隔离库 `127.0.0.1:3307/dating_workflow_test`，需要预先加载基线和三份迁移，不要将地址改成业务数据库：

```powershell
$env:DATING_MYSQL_TEST_URL='jdbc:mysql://127.0.0.1:3307/dating_workflow_test?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Shanghai'
mvn -pl ruoyi-admin -am package
Remove-Item Env:DATING_MYSQL_TEST_URL
```

前端根目录（先启动 Vite，本机需 Chrome 和 Playwright）：

```powershell
npm run build:prod
$env:DATING_UI_URL='http://127.0.0.1:5181'
node tests/dating-billing.browser.mjs
node tests/dating-workflow.browser.mjs
node tests/dating-success.browser.mjs
```

浏览器测试使用模拟接口，不操作真实客户，截图位于 `node_modules/.cache/dating-success-ui/`。本次在隔离 MySQL 8.0.45 验证了第三阶段迁移连续执行两次及结案并发；38 项后端测试、三阶段浏览器回归通过。

这些验证不包含真实业务环境的完整 HTTP、Redis、登录及授权联调。实际业务数据库未执行迁移，成功结案默认关闭；上线前仍需执行升级、部署和验收。
